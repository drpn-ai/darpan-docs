The results page is where a reconciliation earns its keep. It shows which records matched cleanly, which are missing from one side, and which pairs have field-level differences — organized so you can act on what you find rather than dig through a downloaded file.

## Review order

1. From **Ask Darpan**, search by run name or output file name.
2. Open **Open Result: ...**.
3. Confirm the run's source files and **Run steps**.
4. Review the difference buckets and their counts.
5. Open the differences, or download the saved result.
6. Classify each difference as source data, schema, mapping, rule behavior, or expected variance.

## Reading the result page

| Part | What it shows |
| --- | --- |
| Source files | The files each side read, with a download for each while it is kept. Extracts read from a source system are deleted 7 days after the run. |
| **Run steps** | The stages the run went through and how each ended. Collapse it once you have read it. |
| Difference buckets | **Missing from** *system* for each side, and **Rule differences** when any rule failed. A run that checks one system shows a single **Findings** bucket. Select a bucket to filter the list to it. |
| Conclusion tiles | Shown in place of the difference buckets when the run's scope has conclusion rules. See [Conclusions](#conclusions). |
| Rule selector | The panel at the side lists **All** plus each rule, by its name, with its count. Pick a rule to see only the pairs that failed it; the buckets give way to one **Total results** count. |
| **Record search** | Type a record ID to find it in the differences. |
| Download | **Download saved result** saves the full result file. |
| **Notify me** | Sends a message to your chat space when this run finishes. See [Run-completion alerts](/guides/run-completion-alerts). |

The footer links to **Open run**, **View previous runs**, and **Run settings**.

## Conclusions

When a run's scope has conclusion rules, the result names what each finding most likely means instead of leaving the raw difference to be worked out.

- The page summarises by conclusion: one tile per conclusion with its count. **Unexplained** is always shown, always last, and lists the findings no rule could name.
- The **Conclusion** column names each finding. Expand a row to see each system's state, **How Darpan concluded** (the fields the deciding rule tested), and the **Raw record**. A HotWax order or return, or a Shopify return, that was found shows its status and its ids, such as the order name or the return's order.
- Where a conclusion needs a decision, **Stop flagging in rules board ›** opens the rules board with a filter pre-filled. **Keep flagging** leaves the rules as they are.

A run whose scope has no conclusion rules shows the difference buckets as before.

### Edit a run's conclusions

Tenant Admins edit a run's conclusions on their own page. In the run's **Ruleset Manager**, choose the pencil beside **Conclusions** (**Edit conclusions**, or **Set up conclusions** when there are none). The **Conclusions** section on the **Ruleset Manager** is read-only.

The page lists the conclusions in the order they are tried; the first match wins. **Unexplained** is always last. Choose a conclusion to open it. It reads as plain lines, and choosing a line turns only that line into its control. Choose the check mark (**Done with this line**) when it is right.

| Line | Sets |
| --- | --- |
| **Name** | The conclusion, picked from the tenant's names. The plus (**New conclusion code**) adds a name that is not in the list yet. |
| **Explains** | Which rows it is tried on: **any check**, a side's missing rows, the rules, or every finding. |
| **When** | The conditions, one per line, joined by "and". All must hold. The plus (**Add a line**) adds one; the trash icon on a line removes it. |
| **Asks** | The question it answers. |
| **Shows as** | **Shown** (a finding you see), **Expected** (not a finding; counted as expected), or **Hidden** (not a finding; left out of counts). |
| **Fix** | How you fix it, in your own words. Darpan never writes it. |

The arrows move the open conclusion up or down, and the trash icon deletes it. The plus at the end of the list (**Add conclusion**) adds one. **Unexplained** can show as **Shown** or **Expected**, never **Hidden**.

A **When** line picks a side and a field (**Pick what to check**, or **Type a path…** for a field the list does not offer), then a test:

| Test | Holds when the field |
| --- | --- |
| **is one of** / **is not one of** | Is, or is not, one of the values. Type a value and press Enter for each. |
| **is more than** | Is more than the number given. |
| **is less than** | Is less than the number given. A date read as a number (epoch milliseconds) is less when it is earlier, so a return dated before go-live matches. |
| **is more than 0** | Is above zero. |
| **is within … hours** | Holds a time within the given number of hours before the run. |
| **is empty** / **is not empty** | Is empty, or has a value. |

A line can also test whether the side's record **is there**, **is missing**, or **was set aside** by the side's filters, alone or before a field test. On a field inside a list, such as an order's lines, the line says whether **any**, **every**, or **no** item must pass.

Nothing is stored until you choose **Save conclusions**, which saves the whole list at once and returns to the run. **Cancel changes** drops every change. Leaving the page with unsaved changes asks **Discard unsaved conclusion changes?**

## Run history

**View previous runs** opens the history for one saved run, grouped into:

- **In Progress**: runs still working. Open one to watch it.
- **Needs Attention**: runs that failed. Open one to retry it from the step that failed; see [Retrying a failed run](/guides/run-reconciliation#retrying-a-failed-run).
- **Most Recent**: the latest result.
- **Previous Results**: earlier results, newest first.

## Common result categories

| Category | Where it shows |
| --- | --- |
| Matched | Not listed. A matched pair that passes every rule is not a difference. |
| Missing from one side | The **Missing from** *system* bucket for the side that lacks it. |
| Value mismatch | The **Rule differences** bucket, and under each failed rule in the rule selector. |
| Repeated key | Each record under the key is a finding. See [Repeated keys](/reference/reconciliation-runs#repeated-keys). |
| Processing error | The run fails. The run page shows the error, and **Run steps** marks the step that failed. See [Failed run](/troubleshooting/reconciliation-runs#failed-run). |

## Where the numbers come from

Two things shape a difference count before you see it, and both exist to stop you chasing differences that were never real.

### Verification passes

Some differences are an artefact of how a source was read rather than a real gap. A bulk export can be indexed slightly behind the live system, so a record that exists is reported missing.

For sources that support it, Darpan re-checks reported-missing records with a direct point lookup and drops the ones that turn out to be present. The result names **which systems each pass rechecked**, so a count that moved is traceable rather than mysterious. A side is looked up only when its missing records are a small share of the records checked against it, 5% unless its connector sets its own. Above that, the run says the read or the pairing needs fixing and looks nothing up; see [Verification pass skipped](/troubleshooting/reconciliation-runs#verification-pass-skipped). A side is never looked up by an ID of another kind, such as an order ID sent to a returns lookup.

### Structural suppression

Some differences cannot exist by definition, and reporting them buries the ones that can. Where a record's own data proves no counterpart is possible, Darpan suppresses it and says so.

Returns reconciliation carries three such rules on the missing-in-HotWax side, each a logical implication rather than an observed correlation:

| Rule | Why no counterpart can exist |
| --- | --- |
| Whole-order cancellation | The order was cancelled, so the refund is a cancellation, not a return. |
| Superseded return draft | The draft was replaced; the surviving return is the real one. |
| Cancelled-item refund | The refunded lines were never shipped, so the system books an item cancellation rather than a return. |

<Note>
Suppression only applies when the row's own data **proves** the rule. Where the evidence is inconclusive — a truncated view, a field the extract predates — the record stays reported. Suppressing on a "don't know" is the one direction that hides real differences, so Darpan never does it.
</Note>

Together these can move a count substantially. The run's alert reports how many rows each rule removed, and the tallies sum to the rows actually removed. See [Reconcile returns and exchanges](/guides/returns-and-exchanges).

### Reading source labels

Run results name the **system** a file came from — resolved to its proper label rather than showing an internal enum token or the endpoint that fetched it. When both sides of a run are the same system, the labels tell the two instances apart.

## Next actions

- Fix source data when the mismatch is real.
- Adjust schema or field selection when parsing is wrong.
- Adjust rules when business classification is wrong.
- Rerun after correction so the new output preserves evidence. See [Run reconciliation](/guides/run-reconciliation) to start the next run with updated inputs.
