User management is a Darpan admin task — it sits outside the Tenant Admin scope entirely. Knowing where that line is saves time when a Tenant Admin asks why they cannot add someone to their tenant, or when a new team member cannot see the right data after signing in.

If you are a Tenant Admin who needs a user added or a role changed, ask a Darpan admin. See [When to ask a Darpan admin](/getting-started/tenant-admin-quickstart#when-to-ask-a-darpan-admin).

## Where users are managed

Users, tenants, and tenant membership are managed in the **Darpan admin app**, a separate console for platform operators. Only Darpan admins can sign in to it. The Darpan app itself has no user-management screens, and **Ask Darpan** has no user-management commands. The one access step a user starts in the app is a CLI access request; see [CLI access](#cli-access).

## Access model

Users sign in and work inside one **active tenant** at a time. A user's role is set per tenant, so the same person can be a Tenant admin in one tenant and view-only in another.

The active tenant is a server-side preference on the account, not a per-tab setting. Switching it in one tab re-points every open tab.

## Roles

Each tenant membership carries one of four roles:

| Role | View tenant data | Run reconciliation | Edit setup (connections, schemas, runs, rules, automations, tenant settings) | Share connections with other tenants |
| --- | --- | --- | --- | --- |
| Tenant admin | Yes | Yes | Yes | Yes |
| Company editor | Yes | Yes | Yes | No |
| Tenant user | Yes | Yes | No | No |
| Company view only | Yes | No | No | No |

**Darpan admin** is a platform role, not a tenant role. It manages users, tenants, membership, and CLI and AI access across every tenant from the admin app. The exact groups behind it are in [Auth and access](/reference/auth-and-access#roles).

## Create a user and grant access

<Note>
These steps are for Darpan admins. If you are a Tenant Admin, ask a Darpan admin to do them.
</Note>

<Steps>
<Step title="Create the user">

In the admin app, start the create-user flow. It asks for the **username**, the person's **name**, their **email**, and a **temporary password**, then confirms before creating.

Always give an email. Password resets depend on it.

</Step>
<Step title="Add the user to a tenant">

Start the add-member flow. It asks **Which user should join?**, **Which tenant should they join?**, and **Which role should they have?** Pick one of the four roles above.

Repeat for each tenant the user needs.

</Step>
<Step title="Hand over the temporary password">

Share the username and temporary password with the user through a channel you trust. At first sign-in, Darpan asks them to choose a new password before it signs them in.

</Step>
</Steps>

## Expected result

The user signs in, sets a new password, and lands in a tenant they belong to. What they can do there follows the role table above.

## Changing access

In the admin app, a Darpan admin can:

- On the tenant's page, change a member's role or **Remove** them from the tenant. Removing access from one tenant does not affect their other tenants.
- On the user's page, **Reset Password**: sets a new temporary password, signs the user out everywhere, and forces a password change at their next sign-in.
- **Disable** the account: the user can no longer sign in and is signed out everywhere. **Enable** reverses it. A Darpan admin cannot disable their own account.

## CLI access

The Darpan CLI is off by default and set per user, per tenant. A user asks for it in **User settings** under **CLI sessions**: the **CLI in &lt;tenant&gt;** card has **Request access in &lt;tenant&gt;**, then reads **Requested &lt;date&gt;. A Darpan admin will turn it on.** until a Darpan admin approves or declines the request in the admin app. A grant can carry an end date and can be paused or revoked. Darpan admins use the CLI without a grant.

Setup steps for the user: [Set up the Darpan CLI](/getting-started/set-up-darpan-cli). Sign-in lengths and limits: [Auth and access](/reference/auth-and-access#cli-access).

## AI access

The audit agent answers a user only when it is on for the tenant and that user has AI access there. A Darpan admin grants AI access per user, per tenant, for a period and with a spend limit; access pauses on its own when spend reaches the limit. Darpan admins have AI access in every tenant where the agent is on. See [The audit agent](/guides/audits#the-audit-agent) and [Auth and access](/reference/auth-and-access#ai-access).

## Endpoint access per source configuration

Roles govern what a person may do. **Endpoint access** governs something different: which endpoints of a connected system a given source configuration is allowed to read at all.

A connected system usually exposes several endpoints — orders, returns, and so on. A source configuration holds credentials that may legitimately reach only some of them, and a credential that can read more than the reconciliation needs is a wider blast radius than the job requires.

Each source configuration therefore carries an explicit list of enabled endpoints:

- The **catalog** of available endpoints comes from the connector registry, so it reflects what the system actually offers rather than a hand-maintained list.
- The **enablement** is per configuration. Two configurations for the same system can enable different endpoints.
- Endpoints left out of the list are **disabled**, including endpoints added to the registry later. A new endpoint is never silently readable by an existing configuration — someone has to enable it.

Only the endpoints enabled here are offered when you build a run, which is why an endpoint you expect may not appear in the source picker.

<Note>
Darpan reads the current enablement before it will accept a change to it, so a stale panel cannot overwrite a setting someone else just made.
</Note>
