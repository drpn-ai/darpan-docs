---
title: "Set up a reconciliation run"
description: "Create a saved run setup that ties source systems, file types, schemas, and primary IDs together."
---

A saved run is the reusable setup behind every reconciliation — source systems, file types, schemas, and the primary IDs Darpan uses to match records. Creating it takes a few minutes; running it takes one click. The last step of the create flow is the rules board, so the comparison logic is saved with the run. See [Author reconciliation rules](/guides/author-rules).

## Before you start

Confirm:

- The two source systems are known.
- For each source, you know whether it arrives as a **File upload** or through the **API**.
- For file uploads, the file type is known: CSV or JSON. Saved schemas exist for JSON sources, or you are ready to create them from the setup flow.
- For API sources, the connection exists: see [Set up Shopify](/guides/setup-shopify) or [Set up HotWax](/guides/setup-hotwax).
- Each source has a stable primary ID field, or a set of fields that together identify a record.
- The saved run name is clear enough to recognize later from **Open Runs Settings**, **Run Reconciliation**, and automation setup.

## What Darpan saves

| Setup choice | Why it matters |
| --- | --- |
| Run name and description | Identifies the saved setup in run history, automation setup, and result review. |
| Source systems | Tells Darpan which systems are being compared. |
| Source mode | **File upload** or **API** for each side. |
| Config and endpoint | For API sources, the saved connection and the endpoint to extract from. |
| File types and schemas | For file uploads, how to read each input: a saved schema for JSON, or a column list for CSV. |
| Primary IDs | One or more fields that match records across the two sources. |
| Rules and exclusions | The comparison logic applied to matched records. |

## Steps

<Steps>
<Step title="Open the create flow">

On Home, choose **Create Run**. Answer **What kind of run?** with **Sync** (do two systems hold the same records?). **Lifecycle** builds a different kind of run; see [Lifecycle runs](/guides/lifecycle-runs).

You can also open **Ask Darpan** with `Cmd/Ctrl+K` or by clicking Tara, the red panda in the corner, search for **Create Reconciliation Flow**, and open the result. That goes straight to the Sync flow.

</Step>
<Step title="Name the saved run">

Answer **What should this run be called?** with a stable, specific name. Add a short description when the flow asks for one.

</Step>
<Step title="Configure the first source">

Answer **Which system provides the first source?**, then **How should … provide data?** with **File upload** or **API**.

For **API**, choose the saved config for that system, then the endpoint when the config enables more than one. If no config exists yet, use **Add a … config** on the same card.

For **File upload**, choose which data the file holds when the system offers more than one kind, then the file type. For JSON, pick the saved schema that describes it, or use **Create New Schema**. For CSV, a schema is optional: pick a saved column list, or skip and type the column names.

Then choose the primary ID. The picker accepts more than one field: pick several to match on a composite key, such as order ID plus line number. See [Composite matching keys](/reference/composite-matching-keys).

</Step>
<Step title="Configure the second source">

Repeat for the second source. The app requires a different system on each side; choosing the same one shows **Source 2 must use a different system than source 1.**

</Step>
<Step title="Add rules and save the run">

The last card, **How should Darpan compare these two systems?**, is the rules board. Draw the field comparisons and add any exclusions, then choose **Save run**. See [Author reconciliation rules](/guides/author-rules) for how the board works.

Darpan saves the run setup so it can be executed manually or reused by an automation.

</Step>
<Step title="Confirm the setup">

Open **Ask Darpan**, search for **Open Runs Settings**, and confirm the saved run appears. Use **Run Reconciliation** when you are ready to execute it once with files or connection-backed data.

</Step>
</Steps>

## Comparing two instances of one system

The Sync create flow in the app always compares two different systems. The service layer is less strict: it accepts the same system on both sides when the two sides use different source configurations, for example staging against production, or two regional instances that should line up. Runs like that are set up through the API.

The same source on both sides is always rejected, because a source compared against itself has nothing to find. Runs built from file uploads carry no source configuration, so they always need two different systems.

Where both sides are the same system, run results label each side by its source rather than by the system name alone, so the two instances stay distinguishable when you review differences.

## Checking one system

A run can also check a single system and report the rows that answer a question, for example "which NetSuite orders were never billed?". It has no second side, and its result shows one **Findings** bucket.

**Create Run** on Home does not offer one. To build one in the app, choose **New one-system run** while adding a check to an audit (see [Audits](/guides/audits#add-a-check)): the run builder opens with a single side. It can also be created through the API (`facade.ReconciliationFacadeServices.create#RuleSetRun` with `scopeMode` set to `EVALUATE`). Once it exists, it opens, runs, and shows results in the app like any other run, and Home files it under the one system it checks. One-system NetSuite runs can be turned into a run flowchart with **Import NetSuite Checks**; see [Lifecycle runs](/guides/lifecycle-runs#import-netsuite-checks).

## Choosing an API endpoint

When a source system exposes more than one endpoint, Darpan asks which one to extract from, and lists the endpoints enabled for that source configuration.

If only one endpoint is available, the question is skipped — a choice with a single option is not a choice. Endpoints that a source cannot use, and endpoints only reachable through the API rather than a file upload, are filtered out rather than offered and then rejected.

Which endpoints a source offers is controlled per source configuration; see [Manage users and access](/guides/manage-users-and-access).

## Expected result

The saved run can be selected from **Run Reconciliation** and from the automation setup flow. It should clearly show what two systems are compared and which record IDs are used for matching.

## Change rules later

The rules saved with the run can be changed at any time from the **Ruleset Manager**. Open **Open Runs Settings**, open the run, and choose **Edit Rules**. See [Author reconciliation rules](/guides/author-rules).

## Delete a run

The trash icon in the **Ruleset Manager**, **Delete run**, deletes a Sync run together with the generated outputs created for it, after a confirmation. It cannot be undone. A lifecycle's trash icon archives instead; see [Lifecycle runs](/guides/lifecycle-runs#retire-a-run).
