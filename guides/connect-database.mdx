---
title: "Connect a database source"
description: "Reconcile straight from MySQL, PostgreSQL or IBM Db2 with a saved connection and a SELECT that returns the records to compare."
---

Plenty of the data worth reconciling never becomes a file. It sits in a database, and getting it into Darpan has meant someone exporting a CSV on a schedule and hoping the export and the reconciliation stay in step. A database source removes that step: Darpan connects, runs a query you wrote, and feeds the rows into the same reconciliation pipeline that files and APIs use.

A database source is two pieces. A **connection** says where the database is and how to authenticate. A **query** says which records to compare. One connection can carry many queries.

<Note>
The app has no screens for database sources in this release. A database source is set up through the `facade.DatabaseFacadeServices.*` JSON-RPC methods, or by an operator on your behalf. Once saved, it is used by a run or automation like any other source.
</Note>

## Before you start

Confirm:

- You are a Tenant Admin for the tenant, and the correct tenant is active.
- The database is **MySQL**, **PostgreSQL**, or **IBM Db2**. Darpan rejects any other dialect.
- The database is reachable from the Darpan deployment, and you have a username and password for it.
- You have a read-only account. Darpan only ever issues `SELECT`, but a read-only credential means a mistake in a query cannot become a mistake in your database.
- You know whether the server offers TLS, and, if its certificate is signed by a private certificate authority, you have that authority's certificate in PEM form.

## Create the connection

Save the connection with `facade.DatabaseFacadeServices.save#DatabaseSourceConfig`. It is created in the active tenant; connections are tenant-scoped and are not shared across tenants. `list#DatabaseSourceConfigs` and `delete#DatabaseSourceConfig` read and remove saved connections.

<Steps>
<Step title="Describe the server">

| Parameter | Notes |
| --- | --- |
| `description` | A label for the connection. |
| `dialect` | `MYSQL` (the default), `POSTGRES`, or `DB2`. |
| `host` | Hostname or address of the server. Required. |
| `port` | Optional. Left blank, Darpan uses the dialect default: 3306 for MySQL, 5432 for PostgreSQL, 50000 for Db2. |
| `databaseName` | The database to connect to. Required. |
| `username` / `password` | The credential. `username` is required. The password is stored encrypted and is never readable back. On update, a blank password keeps the stored one only while `host`, `port` and `dialect` stay the same; change any of them and the save is refused until you send the password again. |

</Step>
<Step title="Set the TLS posture">

`requireTls` is `Y` by default. Leave it on unless the server cannot offer TLS.

With TLS on, Darpan verifies the server's certificate and hostname, not only that the connection is encrypted. It trusts the public certificate authorities, AWS RDS included, so a managed database with a public certificate needs nothing more.

If the server's certificate is signed by a private authority, pass that authority's certificate in PEM form as `caCertPem`. Darpan then verifies the server against that certificate instead of the public authorities.

<Note>
Verification applies to connections saved before it shipped too. A connection whose certificate cannot be verified stops connecting until its CA is stored as `caCertPem`.
</Note>

</Step>
<Step title="Set the limits">

| Parameter | Default | What it does |
| --- | --- | --- |
| `connectTimeoutSeconds` | 10 | How long to wait for the connection itself. |
| `queryTimeoutSeconds` | 300 | How long a single extraction query may run. |
| `maxRows` | 500,000 | The largest result Darpan will accept from one query. |

<Warning>
Max rows is a hard cap, not a page size. A query that returns more rows than the cap **fails the extraction** — it never silently truncates. That is deliberate: a reconciliation run against a quietly truncated source reports differences that are artefacts of the truncation, and nothing on the result would tell you. If you hit the cap, narrow the query rather than raising the number.
</Warning>

</Step>
<Step title="Check the connection">

Once saved, the connection is covered by the standard connection diagnostics (`facade.SettingsFacadeServices.test#SourceConnection`), which connect and run the dialect's test query. A credential that expires later shows up as a failed check rather than as a failed run.

</Step>
</Steps>

## Write the query

A query belongs to a connection and holds the `SELECT` that produces the records to compare. Save it with `facade.DatabaseFacadeServices.save#DatabaseSourceQuery`, passing the `databaseSourceConfigId` and the statement as `sqlSelect`. The statement is validated before it is stored. `list#DatabaseSourceQueries` and `delete#DatabaseSourceQuery` read and remove saved queries.

<Steps>
<Step title="Write a single SELECT">

The statement must be a single `SELECT`, or a `WITH … SELECT`, with no semicolons. Nothing else is accepted.

Return the fields you intend to reconcile, named as you want them to appear. Column names become the field names Darpan compares on, so alias them into the shape your schema expects rather than reshaping later.

</Step>
<Step title="Add the window placeholders, if the query is time-bounded">

A query may use the named placeholders `:windowStart` and `:windowEnd`. Darpan fills them with the run's window. Both are optional — a query that reconciles a full table needs neither. Any other `:name` placeholder is rejected when the query is validated.

Use them for anything scheduled. A query with no window re-reads the whole table on every run, which gets slower as the table grows and usually compares far more than the run needs.

</Step>
<Step title="Preview it">

`facade.DatabaseFacadeServices.preview#DatabaseQuery` runs the query capped at 10 rows, with a 30-second timeout, and returns the columns and rows. Without a window, the preview reads the last 7 days. Check the column names and a few values before saving: the preview is where a wrong alias or an unexpected null is cheap to notice.

</Step>
</Steps>

## Use it in a run

A run side reads from a database when its source has `sourceConfigType` `DATABASE_QUERY` and the saved query's `databaseSourceQueryId` as its `sourceConfigId`. Ask an operator to set that up. Both sides of a run may be database sources, for example two instances with the same schema and a different `SELECT` per side.

From there it behaves like any other API-backed source: it runs on the automation's date window, and the window fills `:windowStart` and `:windowEnd`.

Because the query fixes the field names, a flat schema matching those column names is usually the right pairing. [Create a schema](/guides/create-schema) can infer one from a CSV sample of the same shape if you have one.

## Expected result

The connection passes its diagnostics check, the query previews the rows you expect with the names you expect, and a run that points at the query extracts those rows.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The dialect is rejected | Only `MYSQL`, `POSTGRES` and `DB2` are supported. |
| Connection times out | The host and port, and whether the Darpan deployment can reach the server at all. Raise the connect timeout only after confirming reachability. |
| TLS fails, or a connection that worked before now fails on TLS | Whether the server offers TLS, and whether its certificate is signed by a private authority whose certificate you have not stored in `caCertPem`. |
| The extraction fails on row count | The query returned more than the max-rows cap. Narrow the query — the cap never truncates. |
| The query is rejected | It must be a single `SELECT` or `WITH … SELECT`, with no semicolons. The error names the rule it broke. |
| A long query is cut off | Raise the query timeout, or narrow the query with the window placeholders. |
| "Unknown placeholder :x (only :windowStart and :windowEnd are supported)." | Rename the placeholder to `:windowStart` or `:windowEnd`. |
| The save asks for the password again | You changed `host`, `port` or `dialect`, so Darpan will not send the stored password to the new server. Send it again. |
| Fields do not line up with the schema | Alias the columns in the `SELECT` to the names the schema expects. |
| The source does not appear for another tenant | Connections and queries are tenant-scoped. Create them in the tenant that will run the reconciliation. |

For the exact error messages, see [Connections troubleshooting](/troubleshooting/connections#database-sources). See [Set up a reconciliation run](/guides/setup-reconciliation-run) for pairing the source into a run, and [Create a schema](/guides/create-schema) for the schema it needs.
