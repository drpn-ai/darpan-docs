title: "Glossary"
description: "Darpan terms as the app uses them."
---

The terms below are the ones the app puts on screen, defined the way Darpan uses them.

| Term | Meaning |
| --- | --- |
| Active tenant | The tenant whose records your reads and writes are scoped to. It is stored on your user account, so switching it in one tab switches it in every tab. |
| AI access | Permission to use the audit agent in one tenant. A Darpan admin grants it per user, for a period and with a spend limit; it pauses when spend reaches the limit. The agent must also be on for the tenant. |
| Ask Darpan | Search-first navigation for app destinations and selected records. Opens with `Cmd/Ctrl+K` or from Tara. |
| Audit | A run type that asks whether what must be true is still true. An audit holds a tenant's statements and the checks that test them, runs every check on its one schedule, and keeps each finding open until a later run clears it. See [Audits](/guides/audits). |
| Automation | A schedule that runs a saved run unattended. It runs its own copy of the saved run's sources and filters, taken when the automation was created. |
| Cause | On an audit finding, the one thing holding the record up (**Stuck on**), read from the systems themselves, with the fix and who owns it (**Do this**). |
| Chat space | A named destination for messages: one Google Chat webhook or one Slack channel, set up in tenant settings. Automations, scripts, audit run updates and your own notification default post to chat spaces. |
| Check | One comparison that tests an audit statement. **Ran** means every read was complete. **Partial** means it found what it could and closed nothing, so open findings stay open. |
| CLI access | Whether the Darpan CLI may act for a user in one tenant. Off by default; a Darpan admin turns it on, pauses it, or ends it. See [Set up the Darpan CLI](/getting-started/set-up-darpan-cli). |
| CLI session | One terminal signed in to the Darpan CLI as you, listed in **User settings** under **CLI sessions** with its host, sign-in time, and expiry. **Revoke** ends one; a password change ends all of them. See [Set up the Darpan CLI](/getting-started/set-up-darpan-cli). |
| Compare ID | The key that identifies a record on each side of a run, built from one or more primary ID fields. Also called the primary ID. |
| Conclusion | What a finding most likely means, named by the run's conclusion rules, with the evidence the deciding rule tested. A finding no rule explains is **Unexplained**. |
| Config version | A saved copy of a tenant's setup, listed under **Tenant Settings** > **Config history**. A version is kept a minute after an audit, check, run, or connection changes, or on **Keep a version now**. Restoring one puts that setup back; finished runs keep their results. |
| Connection | A saved external system or provider setup. Credentials live here, not in the run. |
| Darpan admin | A user who administers Darpan itself rather than one tenant. See [Auth and access](/reference/auth-and-access#roles). |
| Deployment | When and where a saved script runs: a daily time or cron schedule in the tenant's timezone, the chat space it posts to, and, for a script that reads a run result, the saved run whose newest result it reads. **Preview message** runs it without posting; **Send now** posts once. |
| Duplicate | A key that repeats within one source. For each side of a run you choose **Fail the run** or **Report each as a finding**. Reported, every record under the repeated key is a finding, and the key is left out of the compare on both sides. |
| Exclusion filter | A condition on a source that leaves records out of a run before comparison: either the listed values (**Exclude these values**) or everything but them (**Only these values**). |
| Finding | A record a run reports for attention: a difference in a Sync run, a row a one-system check returns, or a record that stopped at a place marked as a finding in a lifecycle. In an audit, a finding is one record breaking one statement. It is **Open** until a complete check stops reporting it, then **Fixed**. |
| Generated output | Files or records produced by a workflow or run. |
| JSON-RPC | Backend request format sent to `/rpc/json`. |
| Lifecycle | A run type that follows NetSuite records from a start record through their stages and shows where each one stopped. Every record lands in exactly one named place. See [Lifecycle runs](/guides/lifecycle-runs). |
| Reconciliation run | One execution of a reconciliation. |
| Result | Reviewable output from a run. |
| Rule set | Which fields a run matches, how records are keyed, and what is excluded. Edited on the rules board. |
| Run flowchart | A run built as a chart of yes/no questions. Each question is one reconciliation, and the questions under it run on its yes or no for the records that reached it. A lifecycle is built on one. |
| Run type | What a run asks, chosen at **Create Run**: **Sync**, **Lifecycle**, or **Audit**. |
| Saved run | The reusable run setup that ties sources, schemas, primary IDs, and rules together, reused across executions. |
| Schema | Saved definition of source data shape. |
| Script | JEXL a tenant writes and runs in Darpan, under **Tenant Settings** > **Scripts**, with no code change. It returns the text to post; returning nothing sends nothing. An **Expression** is one line with no loops and gets 250 ms; a **Script** allows loops and gets 2 s. |
| Source strategy | The way inputs are selected or loaded for a run. |
| Statement | Something a tenant needs to be true, in its own words, in an audit. Checks test it. A statement no check reads is **Not covered**, which is not the same as passing. |
| Sync | Re-deriving an automation's copy from its saved run after the run was edited. |
| Sync run | A run type that asks whether two systems hold the same records. Healthy is zero differences. |
| Tara | The red panda in the corner, Darpan's mascot. She opens Ask Darpan, explains what you rest on, and raises warnings. The name is Hindi for star, and for the one who helps you across. |
| Tenant | The organization whose data and configuration a set of users shares. Every saved record belongs to one tenant. |
| Verification | A recheck, after comparison, of reported differences against a source that supports point lookups, so records that exist are not reported missing. |
