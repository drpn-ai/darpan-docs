Darpan access is session-based: a user signs in, gets a session, and works inside one active tenant at a time, with the role they hold there.

## Tenant scope

A user can belong to more than one tenant. The active tenant decides which records they read and write, and permissions are checked for that tenant, so the same person can hold different roles in different tenants. Another tenant's record ID answers exactly like a missing one.

Confirm the active tenant before saving settings, connections, schemas, saved runs, or automations.

## Roles

Darpan seeds six permission groups. Two are Darpan-wide; the four tenant roles are assigned per tenant. Names are as the admin app shows them.

| Role | Group ID | What it can do |
| --- | --- | --- |
| Super admin | `DARPAN_SUPER_ADMIN` | Everything a Darpan admin has, and the admin app and every `admin.*` method, where tenants, users, memberships, and CLI and AI access are managed. Receives the audit run emails. |
| Darpan admin | `DARPAN_ADMIN` | Works in every tenant as a tenant admin without a membership: sees and edits each tenant's data, uses the CLI without a grant, and has AI access where the agent is on. Edits settings shared by every tenant on the instance, such as AI configuration. Does not use the admin app. |
| Tenant admin | `DARPAN_TENANT_ADMIN` | Views, runs, creates, updates, and deletes the tenant's data, and talks to the audit agent. Only a tenant admin shares a configuration with another tenant, changes who gets an audit's run email, schedules a query, and creates GraphQL agent keys for the tenant. |
| Company editor | `DARPAN_COMPANY_EDITOR` | Views, runs, creates, updates, and deletes the tenant's data, and talks to the audit agent, without the tenant-admin-only actions above. |
| Tenant user | `DARPAN_TENANT_USER` | Views tenant pages, uploads files, and runs: plays an audit, resolves a finding or re-checks all of them, starts a saved run, a one-off comparison or a reconciliation. Saves and deletes connections (NetSuite, Shopify, HotWax, SFTP and database). Cannot change other setup or talk to the audit agent. |
| Company view only | `DARPAN_COMPANY_VIEW_ONLY` | Views tenant data. Cannot run or change anything, except to acknowledge an audit finding and send Darpan feedback on one, which every role can do. |

**Darpan admins** are users in either Darpan-wide group; the framework's built-in `ADMIN` group counts as a Super admin. A Darpan admin reaches every tenant as a tenant admin, with no membership to add. The admin app and every `admin.*` method need Super admin. A super admin adds or removes the Darpan admin and Super admin roles on a user's page in the admin app; their own Super admin role cannot be removed there.

## Session lifecycle

- Sign-in: `login#Session` returns a login-key token and also sets the HttpOnly `darpan_login_key` cookie. Read `authenticated` in the result to know whether a session exists.
- Lifetime: a web sign-in ends after 60 minutes with no request, and 24 hours after sign-in at the latest. Each request moves the idle end on. `authTokenExpiresInSeconds` reports the 24-hour end, and the cookie expires then too. There is no refresh call: sign in again to get a new token.
- Two-factor: when two-factor is on or required, a right password does not sign in on its own. `login#Session` answers with a challenge (`twoFactorRequired` or `twoFactorSetupRequired`) instead of a token, and `verify#SignInCode` finishes the sign-in with a code, a recovery code or a passkey assertion. See [Two-factor](#two-factor).
- Passkey alone: where passkeys are offered, the sign-in page asks for the username first and its field's autofill offers saved passkeys, which need no password; **Use a passkey or security key** on the password step scopes the prompt to the typed username. `begin#PasskeyFirstSignIn` returns the options and a one-use token, and `finish#PasskeyFirstSignIn` answers as a completed `verify#SignInCode` does. A security key needs the username typed first; a passkey kept on the device needs none. Password plus code stays as the fallback, and an account that must change its password is asked to sign in with the password once.
- CSRF bootstrap (browser): `GET /apps/darpan/csrfToken` restores the session from the cookie when present and returns `{"moquiSessionToken": "<token>", "authenticated": true|false}`. Send the token in the `X-CSRF-Token` header on later `POST /rpc/json` calls. Header-token callers skip this step.
- Sign-out: `logout#Session` revokes the token on the current request (header or cookie) and ends only that session. `logout#AllSessions` revokes every login key for the user, which signs them out on every device.
- Password: a new password needs at least 12 characters, one number and one symbol, and cannot repeat one of the last five. `verify#OwnPassword` checks the current password without changing anything. `change#OwnPassword` changes it for a signed-in user and revokes every other login key, CLI sign-ins included; the current session stays. When sign-in reports `passwordChangeRequired`, use `change#ExpiredPassword`, which needs no session; then sign in again.
- Active tenant: the active tenant is stored as a preference on the user, not on the session. Switching tenant with `save#ActiveTenant` changes it for every session of that user, including other browser tabs. Give integrations their own user rather than sharing a login with a browser user.

## Forgot password

**Forgot password?** appears under **Sign In** only when the instance can send email; `get#PasswordResetStatus` reports whether it can.

| Method | What it does |
| --- | --- |
| `request#PasswordReset` | Emails a 6-digit code to the account's recovery email. The code expires in 15 minutes; requesting again replaces it. |
| `verify#PasswordResetCode` | Checks a code without using it up. Five wrong guesses end the code. |
| `complete#PasswordReset` | Sets the new password, signs the account out on every device, and emails a notice. Issues no token: sign in afterwards. A disabled account is refused. |
| `save#RecoveryEmail` | Saves the signed-in user's recovery email. Requires the current password; an address another account uses is refused. |

## CLI access

CLI access is set per user, per tenant, and is off by default. A user asks for it in **User settings** under **CLI sessions**; a super admin approves or declines in the admin app. A grant can carry an end date and can be paused, unpaused, or revoked. Darpan admins, super admins included, use the CLI in every tenant without a grant. Setup steps: [Set up the Darpan CLI](/getting-started/set-up-darpan-cli).

- Lifetime: every tenant CLI sign-in lasts 7 days, whatever the role, Darpan admins included. The admin CLI sign-in lasts 12 hours (see below).
- Sign-in: `darpan login` prints a code; the user approves it on **Approve CLI** (`/cli-login`) within 10 minutes. The password never goes through the terminal. With two-factor on, approving also takes a current code from the authenticator app or a passkey.
- Every call is checked against the tenant it reaches. It is refused when access there has ended, is paused, or is revoked, or when the tenant sign-in is older than 7 days; run `darpan login` again.
- When a role requires two-factor and the user has not set it up, CLI calls are refused with "Two-factor is required for this account. Set it up in the Darpan app, then run darpan login again."
- **Revoke** in **CLI sessions** ends one sign-in; a password change ends all of them.
- Admin CLI: `darpan-admin` signs in by browser approval. It prints a link and an 8-character code; the person opens the link in the Darpan app, types the code from the terminal, and approves with a fresh passkey or authenticator code. Only a super admin can approve an admin sign-in. It lasts 12 hours, is kept between commands until it ends or `darpan-admin logout` is run, and is the only CLI sign-in that can call `admin.*`. A tenant CLI sign-in is refused there with "... is not available to the Darpan CLI; use the app."
- Reach: a CLI sign-in can call only `/rpc/json` and `/rest/s1/graphql`, and on `/rpc/json` only the methods the CLI allows: reads that return no credentials, run starters, and queries and their schedules.

## Two-factor

Two-factor adds an authenticator-app code (6 digits, a new one every 30 seconds) or a passkey after the password. A person can hold the app, up to ten passkeys, or both, and gets ten one-time recovery codes when the first factor goes on. Setup steps: [Two-factor sign-in](/guides/two-factor).

| Item | Value |
| --- | --- |
| Roles it can be required for | Super admin, Darpan admin (and the framework's `ADMIN`), Tenant admin in any tenant, or everyone: every person with a tenant membership or a Darpan role. Optional for every role until a super admin sets a date. |
| Before the required date | Each sign-in asks the person to set it up, and they can skip. Anyone a dated requirement covers (a role, or everyone) and who has no factor gets reminder emails. |
| From the required date | A person who has not set it up is taken into setup at sign-in, not locked out; the sign-in finishes once a factor is on. |
| Wrong codes in one sign-in | 5 end the sign-in. Each wrong code also counts as a failed sign-in toward the 3-failure, 5-minute lockout. |
| Wrong codes in 24 hours | 20 lock codes until a password reset or an admin reset, and the person is emailed. |
| A code | Accepted once. |
| Emails | Setting up the app, adding a passkey, using a recovery code, a code lock, and an admin reset each email the person. |

- Dates are on the UTC calendar: a requirement dated for a day starts at 00:00 UTC. A super admin sets the date.
- Reminders: each person a dated requirement covers (a role, or everyone) who has no factor set up and has an email address gets a reminder when the date is set, again as the date nears, then weekly, at most one a day. They stop once a factor is on.
- A fresh code or passkey is asked for when approving a CLI sign-in, making new recovery codes, changing or turning off a factor, and on admin actions such as a config transfer export or a two-factor reset.
- Turning two-factor on or off, and an admin reset, end every other sign-in of the person, web and CLI. The tab that made the change stays signed in. Adding or removing a factor that is not the last ends nothing.
- The last factor of a person whose role requires two-factor cannot be removed.
- A password reset never turns two-factor off; it clears a code lock.
- A super admin resets a person's two-factor from the person's page in the admin app with **Reset two-factor**, giving a reason and their own code. It removes the app, passkeys and recovery codes and ends the person's sessions and CLI keys.
- Passkeys are offered only where the Darpan instance has a passkey address configured and the browser supports them.

## AI access

The audit agent answers only when it is on for the instance and the tenant, the user is a Tenant admin or Company editor there, and the user has AI access there. A super admin grants AI access per user, per tenant, in the admin app, for a period and with a spend limit, and can pause, unpause, or revoke it. Access pauses on its own when spend reaches the limit. Super admins have AI access in every tenant where the agent is on, with no per-user limit. A Tenant user or Company view only member is refused with "Only editors and tenant admins can talk to the agent." See [Audits](/guides/audits#the-audit-agent).

## GraphQL agent keys

A tenant admin's GraphQL agent key lasts at most 90 days, the default maximum. A key minted with no expiry gets the maximum, and a later expiry is refused. Each key records who minted it. Endpoint and key details: [GraphQL API overview](https://developers.drpn.ai/graphql/overview).

## Request fence

`/rpc/json` answers HTTP 403 for any method outside `facade.*`, `admin.*`, and `gql.*`, before dispatch. The framework's `/rest/login` is closed.

Darpan signs people in only through `login#Session` and its two-factor step. HTTP Basic credentials, and a username and password sent as request parameters or inside a request body, are refused with HTTP 401 on every route, whether the password is right or not. API clients use a session or an API key.

## Sensitive auth values

Examples use placeholders for usernames, passwords, session cookies, login keys, CSRF tokens, and other auth values.
