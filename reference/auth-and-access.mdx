title: "Auth and access"
description: "How sessions, active company and active tenant scope, and protected backend calls work."
---

Darpan access is session-based; users sign in, receive a session, and operate within the active company or active tenant available to them.

## User context

Some users may belong to more than one company or tenant. When that is enabled, the active company or active tenant controls which scoped records they read and write.

## Permission context

Permissions are evaluated for the active company or active tenant. A user can have different capabilities in different companies or tenants.

## Product roles

| Role | Typical scope |
| --- | --- |
| Super Admin | Manages Darpan platform settings, users, tenants, permission assignments, and tenant data. |
| Tenant Admin | Manages tenant-owned settings, connections, schemas, saved runs, automations, and results for the active tenant. |
| Tenant User | Views tenant data, uploads files, runs reconciliation, and reviews output without changing tenant setup records. |

Tenant Admins should confirm the active tenant before saving settings, connection records, schemas, saved runs, or automations.

## Sensitive auth values

Examples use placeholders for usernames, passwords, session cookies, login keys, CSRF tokens, and sensitive auth artifacts.

## Session lifecycle

- Sign-in: `login#Session` returns a login-key token and also sets the HttpOnly `darpan_login_key` cookie. Read `authenticated` in the result to know whether a session exists.
- Lifetime: the token lasts for the server's login-key expiry, 144 hours (6 days) by default; `authTokenExpiresInSeconds` reports it. The cookie expires at the same time. There is no refresh call: sign in again to get a new token.
- CSRF bootstrap (browser): `GET /apps/darpan/csrfToken` restores the session from the cookie when present and returns `{"moquiSessionToken": "<token>", "authenticated": true|false}`. Send the token in the `X-CSRF-Token` header on later `POST /rpc/json` calls. Header-token callers skip this step.
- Sign-out: `logout#Session` revokes the token on the current request (header or cookie) and ends only that session. `logout#AllSessions` revokes every login key for the user, which signs them out on every device.
- Password: `verify#OwnPassword` checks the current password without changing anything. `change#OwnPassword` changes it for a signed-in user. When sign-in reports `passwordChangeRequired`, use `change#ExpiredPassword`, which needs no session; then sign in again.
- Active tenant: the active tenant is stored as a preference on the user, not on the session. Switching tenant with `save#ActiveTenant` changes it for every session of that user, including other browser tabs. Give integrations their own user rather than sharing a login with a browser user.
