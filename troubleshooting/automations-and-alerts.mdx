title: "Automations and alerts"
description: "Diagnose scheduled automations that did not run and missing run-completion alerts."
---

Automations run on schedule, and alerts fire when they finish. When neither happens, the issue is almost always in the setup — a credential, a schedule, a webhook URL, or the active tenant context. These checks walk through both failure modes.

## Automation did not run

An automation has a saved run, an input mode, and a schedule. If a scheduled run never fired, start by confirming all three are still correct.

**Check the automation record**

Open **Ask Darpan**, search for **Open Automations**, and open the result. Confirm the row shows the expected input mode, schedule, state, and next run.

If the automation is not on the list, it was deleted with the trash icon. That archives it: an archived automation never fires, scheduled or otherwise. Its history is kept, and `facade.ReconciliationFacadeServices.restore#Automation` brings it back; the app has no restore control.

**Check whether an audit owns it**

If **Schedule** shows **Set by audit** *name*, the automation runs one of that audit's checks. It runs when the audit runs, on the audit's schedule, and is not scheduled or paused on its own. Check the audit's settings instead: a new audit's **Daily** schedule is off until you turn it on. See [Audit settings](/guides/audits#audit-settings).

**Check whether it is waiting in the queue**

A scheduled run that fired may be waiting for a free slot: an instance and each tenant run only so many at once. A waiting run has no run record yet, so the automation can look as if it did not fire. It starts when a slot frees up. See [Run queue](/reference/reconciliation-runs#run-queue).

**Check the input sources**

- If the automation uses **SFTP file inputs**: confirm the SFTP server is reachable and the remote file paths are populated. If no SFTP server appears, create or reactivate the required server from **Open SFTP Servers**.
- If the automation uses **API date-range extraction**: confirm the API source is reachable. If no source appears, confirm the relevant system setup from [Set up Shopify](/guides/setup-shopify) or [Set up HotWax](/guides/setup-hotwax).

**Check the saved run**

When the automation asks **Which saved run should this automation use?**, it points to a specific saved reconciliation run. If that run was deleted or its sources removed, the automation cannot execute. Confirm the saved run still exists and its sources, schemas, and primary IDs are intact. See [Set up a reconciliation run](/guides/setup-reconciliation-run) to recreate it if needed.

**Check whether the automation gave up**

A scheduled execution that fails for a transient reason, such as a source timing out, is retried automatically. When the retries run out, the execution is marked dead-lettered (`AUT_STAT_DEAD_LETTER`), a failure alert is sent naming the last error, and no further retries happen for that execution. Fix the cause, then wait for the next scheduled run, or re-drive the execution through the API with `reprocess#AutomationExecution`.

**Run it now to watch it**

The run button on the automation dashboard starts the automation immediately and opens the live run view, which advances stage by stage. If the run fails, the live view shows the full error text.

**If a run appears permanently stuck**

A server crash or restart mid-run can leave a run result in a running state, which blocks re-triggering. A scheduled sweep marks run results that have been running or pending for more than 120 minutes as failed, with a status message saying why. No action is needed: wait for the next sweep, then trigger the automation again.

<Note>
The sweep has no manual trigger. If a run stays stuck for longer than 120 minutes and is not swept, [report it](/releases/bug-reports) with a link to the run.
</Note>

## Alert never arrived

Run-completion alerts post a message to Google Chat or Slack when any reconciliation run reaches a final state — manual or automated, succeeded or failed. A run reports to the chat space its automation is linked to, plus the space of anyone who subscribed with **Notify me**. Registering a space in Tenant Settings does not by itself route any run to it, which is the most common reason a correctly configured space stays quiet.

<Note>
Notification delivery is best-effort. A run never fails because an alert could not be sent. The run result is always saved and viewable in the app regardless of whether the alert fired.
</Note>

| Symptom | What to check |
| --- | --- |
| No message arrives after a run | Confirm something routes the run to a space: the automation is linked to one, or you subscribed with **Notify me**. Then confirm the space is active, still has its delivery target (a webhook, or a Slack channel), and belongs to the run's tenant. |
| One automation's alerts stopped, others still arrive | Its linked space was deactivated or lost its delivery target. Darpan logs a warning naming the dropped space. Relink the automation or reactivate the space. |
| **Notify me** does not subscribe | You have no default chat space set. Set one in **User Settings**, then subscribe again. |
| Alerts arrived for older runs but not this one | Subscriptions cover a single run and are cleared once it finishes. Subscribe again on the new run. |
| A Google Chat space save is rejected | The webhook URL must be `https` on `chat.googleapis.com`, target a space messages endpoint, and include `key` and `token` query parameters. |
| A space cannot be deleted | An automation or an active subscription still references it. Deactivate it instead. |
| An automation save is refused with **Chat space '…' was not found or is inactive.** | The space is inactive, or belongs to another tenant. An automation can link only a space of its own tenant. |
| A space's chat product cannot be changed | A space's product is fixed once created. Add a new chat space instead. |
| A space shows **Slack · webhook** rather than **Slack · bot** | It is an older Slack space that posts through an incoming webhook. It still delivers, and editing it keeps the webhook. New Slack spaces post through a connected workspace. |
| Message arrives but the link does not open the result | Confirm the run produced a saved result and that the app base URL for the environment is reachable. |
| Alerts stopped after a tenant switch | Chat spaces are per tenant. Confirm the active tenant matches the runs you expect alerts for. |

**Run-result link points to the wrong URL**

The link in the alert derives its base URL from the `DARPAN_APP_BASE_URL` environment variable or the `darpan.app.baseUrl` property, falling back to the first allowed origin. If the link opens the wrong environment, verify these settings on the server side.

**Set up or update a chat space**

To add, rename, or deactivate a chat space, go to [Run-completion alerts](/guides/run-completion-alerts). The registry lives in **Tenant Settings** under **Operations → Notifications**, and only Tenant Admins can save changes there.

Choosing your own default space in **User Settings** and using **Notify me** on a run are personal preferences and need no tenant write access.

## Automation no longer matches its saved run

An automation is a snapshot of a saved run taken when the automation was created, not a live pointer at it. Editing the run afterwards leaves the automation as it was.

Darpan reports the drift, naming the fields that differ. Use **Sync** to re-derive the snapshot from the run — it overwrites the compare scope, input mode, source definitions and exclusion filters, and preserves the name, schedule, window, chat space, active status and SFTP details.

If **Sync** is refused, the saved run no longer exists and the automation has to be recreated. An automation can never be pointed at a different run; that is fixed for its lifetime.

## A schedule fires at the wrong hour, or covers the wrong day

Each automation stores its own timezone. When the automation is created, the timezone defaults to the tenant's, and it stays pinned to that zone afterwards. Changing the tenant timezone later does not move existing automations.

A pinned zone that does not match the tenant's business day does more than shift the clock: the automation's date window is computed in its own zone, so it reconciles the wrong day.

The automation's schedule shows the zone it runs in. Check that first, rather than converting the schedule hours to compensate. To correct it, edit the automation and pick the right **Timezone** on the schedule card. See [Set up an automation](/guides/setup-automation#timezone).

A weekly automation whose window crosses a month boundary fires once. Only a window longer than 28 days is split at month boundaries.

## Slack alerts specifically

| Symptom | What to check |
| --- | --- |
| Slack messages fail for one channel only | The Darpan app is not in that channel. Invite it. Private channels always require an invite. |
| Slack rejected the bot token | The token must start with `xoxb-`. A `xoxp-` user token is refused by shape, because it would post as the person who created it. |
| **Connect Slack** is not offered | The deployment has no Slack app credentials configured. Use **Connect with a bot token** instead. |
| Channel listing fails after connecting | The token is missing scopes. Darpan names the missing scopes when the token is saved; add them in Slack and paste the token again. |
| A workspace cannot be disconnected | Chat spaces still post through it. Darpan names them; repoint or delete those spaces first. |
| **That Slack channel is archived. Pick an active channel.** | Edit the space and pick an active channel. |
| **The Slack app is missing a permission it needs. Reconnect the workspace to grant the current scopes.** | In the Slack menu, use **Reconnect workspace**, or **Replace bot token** with a token that has the current scopes. |
| A webhook URL save is refused | For a **Slack · webhook** space, the URL must be `https` on `hooks.slack.com` and target an incoming webhook endpoint. "Slack webhook URL is incomplete" means part of it is missing: copy the whole URL from the Slack app's **Incoming Webhooks** page. |

## An alert looked clean but differences existed

A saved run's difference count includes value mismatches: it is records missing from one side, plus rule differences, plus duplicate records. A run with no missing records but many value mismatches has a non-zero difference count. See [How differences are counted](/reference/reconciliation-runs#how-differences-are-counted).

The alert's **Details** block lists the counts separately: **Missing from** each side, then one **Mismatch** line per named rule, busiest first. Mismatches not tied to a named rule are pooled into one **Field mismatches: N** line. Read those lines, not only the verdict. See [Review results](/guides/review-results).
