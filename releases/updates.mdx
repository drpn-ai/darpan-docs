Darpan releases from newest to oldest, with product and operator changes that affect upgrade, validation, or rollback decisions. Only tagged releases appear here. For release principles and review questions, see [Release discipline](https://developers.drpn.ai/engineering/release-discipline).

Version key: headings carry the backend version (`drpn-ai/darpan`); the app (`darpan-ui`) has its own tags, named in each entry: `v2.x` alongside backend `v1.x`, `v3.x` from backend `v2.0.0`, and `v4.x` from backend `v3.0.0`. Backend and app tags are cut together for major and minor releases. A patch can be backend-only or carry an app tag too, as `v1.5.1` did with app `v2.6.1`.

## v3.5.1 — November 2026

Cut with app `v4.4.15` and `darpan` CLI `0.6.0`; `darpan` 3.5.1 is the build to deploy. 3.5.1 lets a sync pulse watch Shopify → HotWax orders and keeps errors and warnings out of your chat rooms. A minor release that moves the API contract to version `6`, because the order lookup's catalog methods are removed. The theme: look up any id from what Darpan already holds, without calling your systems.

### Look up any id

- `darpan lookup` answers from an index of every id Darpan reads, in runs, audits and kept copies, and never calls Shopify, HotWax or NetSuite. An order id finds the order in each system and the records it connects to, with its open findings. An id Darpan has not read yet comes back as not seen. With CLI `0.6.0`.

### Busy days

- A sync pulse can now watch a Shopify → HotWax check: it reads the recent Shopify orders, asks HotWax which it holds, and names the ones still waiting past your allowance, every 1 to 6 hours. Choose the Shopify side as the **Upstream side**. See [Peak periods and sync pulse](/guides/peak-periods-and-sync-pulse).

### Audits

- Errors and warnings go to the Darpan team's alerts room, never your chat room (3.5.1). The audit update's chat card and the digest's chat message no longer say a check did not run; the email still does. An automation's own chat space is no longer posted a run error; **Notify me** still is. The update after a run goes out once a morning, after every due check has run, not again as late checks finish.
- Acknowledging a finding no longer needs a note (app `v4.4.15`): leave the box empty and choose **Acknowledge**. The card then shows who and when.
- A play can run only the checks you name, through the API (`run#Audit` `checks`).

### Operators

- 3.5.0 moves `darpan`, `darpan-hotwax` `v1.4.0`, `shopify-darpan` `v0.12.0` and `netsuite-darpan` `v0.8.0` together: the system components carry the index's sources. Its upgrade data (4 records, loaded on boot) adds the tenant filters of the ID index tables and the nightly index job, which arrives paused. Run the pending migrations after the deploy (the acknowledgement note becomes optional), then deploy app `v4.4.15`. CLI `0.5.0`'s `lookup --all` and catalog commands stop working; CLI `0.6.0` replaces them.
- 3.5.1 moves `darpan` alone, on 3.5.0's other pins. Its upgrade data (4 records, loaded on boot) marks HotWax orders and Shopify orders as the systems a pulse can read upstream and rewords two mascot lines; its alerts change (DAR-BE-378) adds no data. There is no migration of its own.

## v3.4.16 — November 2026

Cut together with app `v4.4.0` and `darpan` CLI `0.2.4`; `darpan` 3.4.16, app `v4.4.14` and CLI `0.5.0` are the builds to deploy. 3.4.1 gives automations back their own copy of the filters; 3.4.2 makes **Run now** read both sides in the run's own tenant and checks every unmatched exchange; 3.4.3 gives queries their own page and lets a NetSuite order line carry its order's backorder; 3.4.4 looks up every record a regular run's read could not confirm, opens the audit page on the last morning that was due, and gives audit findings a priority, which app `v4.4.4` lets you work through on the audit page; 3.4.5 lists under each audit statement only the causes it can reach, gives a Shopify order on its way to NetSuite its day of grace, and lets a HotWax orders side keep exchange orders; 3.4.6, with app `v4.4.7`, sends a run's errors to the Darpan team instead of your chat space, re-checks HotWax orders that changed since an audit's last read, and shows each system's payment status on a finding; 3.4.7, with app `v4.4.10`, lists an order finding's lines with each system's word for them, and sends a failed saved run's error to the Darpan team instead of your chat space; 3.4.8 makes those lines a read option you tick on a run's side; 3.4.9, with app `v4.4.11`, lets you acknowledge an audit finding with a note, send Darpan feedback from a finding, and re-check every open finding at once; 3.4.10, with app `v4.4.12`, lets you switch a run's read options on its page after it is made. 3.4.11, with CLI `0.3.0`, lets the CLI make any change your role allows in the app; 3.4.12, with app `v4.4.14`, makes every audit finding speak of the systems its check compares, in the same rows, and adds the methods behind proposing an audit change yourself; 3.4.13 follows an order id through every connected system for the CLI and keeps the record an audit check looked up. A minor release that moves the API contract to version `5`, because methods are removed. It adds 25 methods, for peak periods, the sync pulse, the audit read report and queries (and 3.4.3 one more, for pinned queries, 3.4.9 seven, for acknowledgements, feedback and re-checking all findings, 3.4.12 three, for proposing an audit change, and 3.4.13 six, for looking up an order), and removes the 8 tenant script methods that queries replace. The theme: Darpan stays light on your busy days, every run filters its records the same way, and you can ask your own questions of what your audits keep.

### Busy days

- Peak periods: name a sale week in **Tenant Settings**. Darpan moves the runs you choose, holds scheduled runs out of the peak hours, keeps its HotWax reads inside a share you pick, and can send NetSuite one request at a time. See [Peak periods and sync pulse](/guides/peak-periods-and-sync-pulse).
- Sync pulse: attach a pulse to a daily HotWax check and it counts the orders still waiting in the other system every 1 to 6 hours. It posts to a chat space when orders pass the allowance you set, and again when none are left. The daily check then starts after the allowance, and its rows say which orders the pulse flagged first.

### Runs and results

- Every run applies a side's filters after the read and before the compare, manual and scheduled alike. Records a filter leaves out are set aside and counted, and a conclusion can test for them. HotWax exchange orders, cancelled HotWax returns and NetSuite payment lines are set aside the same way. See [Filters and set-aside records](/reference/reconciliation-runs#filters-and-set-aside-records).
- A side with filters but no key, or whose records are not the extract's top-level records, fails before it reads instead of comparing records you meant to leave out. See [A side cannot be filtered](/troubleshooting/reconciliation-runs#a-side-cannot-be-filtered).
- A run no longer warns about keys on more than one record when a conclusion rule hides every repeated-key row; a repeat no rule explains still warns. See [Repeated keys](/troubleshooting/reconciliation-runs).
- Lookups are a last resort, and never by an ID of another kind. A regular run looks up every record its read could not confirm, and adds a note when that was more than 5% of the records checked against a side (3.4.4; 3.4.0 to 3.4.3 looked nothing up above that share). Only an audit's checks, which read the period so far, still look nothing up above it. See [Verification passes](/guides/review-results#verification-passes).
- A returns run grades its returns (sync grace, before the window, cancelled-order refunds) before any lookup, so it no longer warns about records that grading clears (3.4.4).
- A found HotWax order or return, or a Shopify return, shows its status and ids in a run's expanded row.
- An automation run that fails, or whose side read or kept no records while the other side read some, no longer posts its error to the automation's chat space (3.4.6). A scheduled run's space gets one line that day: "*name* did not run this morning. Darpan has been alerted and is working on a fix." **Notify me** gets the same line. The error goes to the Darpan team. See [When an automation run does not run](/guides/run-completion-alerts#when-an-automation-run-does-not-run).
- A side whose key is a plain field name, with no record path, is filtered on each record (3.4.6). Such a run failed at the compare.
- A saved run you start by hand that fails, or whose rules could not run, no longer sends its error to **Notify me** (3.4.7). Each subscriber gets one line: "*name* did not finish. Darpan has been alerted and is working on a fix." The error goes to the Darpan team. See [When a saved run you started fails](/guides/run-completion-alerts#when-a-saved-run-you-started-fails).
- A HotWax orders side can keep its exchange orders and compare them like any other order (3.4.5). Turn on **Keep exchange orders** when you set up the side; it is off by default, so every run reads as before. See [Exchanges](/guides/returns-and-exchanges#exchanges).
- The Darpan CLI can make any change your role allows in the app (3.4.11, CLI `0.3.0`). That covers runs, automations, audits and their statements, peak periods, sync pairs, notification routes, queries and their schedules, finding acknowledgements, **Config history** restores, and the audit agent's proposals. A change is sent only with `--yes`. Connection credentials, sign-in, two-factor, passkeys, CLI access, and Shopify or Slack installs stay in the app. See [Set up the Darpan CLI](/getting-started/set-up-darpan-cli#make-other-changes).
- Only an editor can switch which endpoints a connection reads (3.4.11). A view-only member could switch them.
- A run's read options can be changed after it is made (3.4.10, app `v4.4.12`). The run's **Ruleset Manager** lists them in **Read options**, under **Filters**: **Keep exchange orders**, **Order items**, **Order lines** and the returns switches, each with a switch that saves the run at once. Before, you picked them only while creating the run. An automation reads the change after **Sync**. See [Exchanges](/guides/returns-and-exchanges#exchanges).
- An automation runs on its own copy of its saved run's filters, as it does its sources. A filter edit on the run reaches the automation's scheduled and audit runs only after **Sync**, and the automation names the side whose filters differ (3.4.1; 3.4.0 had automations read the run's filters live). A config bundle or version saved on 3.4.0 carries no automation filters: importing or restoring it gives each automation its run's filters. See [Keep an automation in step with its run](/guides/setup-automation#keep-an-automation-in-step-with-its-run).
- **Run now** reads both sides of a run in the tenant you started it in (3.4.2). A run started from a tab or the CLI in one tenant, while your saved tenant was another, could read its second side without the fields its rules need: every order an **Item Sync** mismatch, or half the returns missing. Scheduled runs were not affected.
- The exchange presence check looks up every unmatched exchange in the window (3.4.2). It stopped at 200 and reported the rest as deferred, so a weekly window left most exchanges unchecked. See [Returns and exchanges](/guides/returns-and-exchanges).
- Conclusions have their own page. The pencil beside **Conclusions** in the **Ruleset Manager** opens it: each conclusion reads as plain lines and edits one line at a time, and **Save conclusions** saves the list once. A condition can test **is less than**. See [Edit a run's conclusions](/guides/review-results#edit-a-runs-conclusions).
- A conclusion can test whether a field starts with one of several prefixes, case ignored, such as an exchange order's `EXC-` lines (3.4.4). Darpan sets it up for now; the conclusions page shows such a line without its test.

### Queries

- Tenant scripts are now queries. Type a question in **Ask** and the agent writes a read over what your audits keep (a dataset's kept fields, a saved run's newest result, an audit's findings) and a script, and runs it before you see it. The answer is a summary and up to five CSV files. See [Queries](/guides/queries).
- Queries have their own page (3.4.3): **Queries** on the Dashboard, or Cmd+K. Like the Dashboard, it shows your **Pinned Queries** first (drag a query there; pins are yours, per tenant), then the rest grouped by what they read. Tenant Settings no longer lists them, and old links still open the same query.
- A query reads top to bottom (3.4.3): **Data**, **Script**, **Result**. **Data** says in a sentence what it reads; select it to pick an audit's findings, a run's result or kept records by name in the **Data** popup, with the days, conditions and fields to keep. The read's JSON is one icon away.
- A Tenant admin can schedule a query daily. It emails the summary and the files to any address, and can post the summary to a chat space. It sends as whoever saved it, and switches off if that person is no longer a Tenant admin of the tenant. Once a query has a schedule, only a Tenant admin can change it, and a config restore or import that changes it switches its schedules off. Every emailed file is logged with its recipients.
- Your scripts are moved for you. Each becomes a query with the same name and code, and each schedule arrives switched off, still posting to its chat space, until a Tenant admin switches it on. A script that read a run result arrives switched off too: its rows now arrive flat, so check it before switching it on. See [A schedule from before 3.4.0 stopped posting](/troubleshooting/queries#schedules).

### Audits

- A HotWax order NetSuite lacks that was less than a day old when read is named **On its way to NetSuite**: expected, not a finding. Past that, an exchange whose return already has its RMA and credit memo is named **Exchange not sent, return credited**. From 3.4.5 the same grace covers a Shopify order HotWax already holds, so a check for Shopify orders missing from NetSuite no longer reports one placed minutes ago. See [Orders on their way to NetSuite](/guides/audits#orders-on-their-way-to-netsuite).
- A NetSuite sales order line can carry its order's totals (3.4.3): a query over sales order lines may ask, on every line, for a sum or list over all the order's lines, such as the backordered quantity and the SKUs on backorder. A conclusion can then name one store backorder once for the order instead of three causes across its lines.
- A check on no statement does not run. An import or restore that takes a check off its last statement retires it, so it no longer reads your systems every morning for nothing.
- The update after each run says how often the run read your systems, and how many reads could cost less. Under **No cause named yet**, the email now asks **Know why? Explain them to the agent**, opening the statement with the **Agent** tab (3.4.4).
- The audit page opens on the last morning that was due (3.4.4). Before the audit's scheduled time it shows yesterday's morning, instead of an empty today that read as not complete and offered to retry checks not yet due. See [Read the audit page](/guides/audits#read-the-audit-page).
- Statements and findings carry a priority, `P0`, `P1`, `P2` or `KNOWN`, and a cause can set its own (3.4.4). The report counts open findings at each level, and findings filter by level over [GraphQL](https://developers.drpn.ai/graphql/changelog).
- The audit board switches between **Record type** and **Priority** at the head of its first column (app `v4.4.4`). By **Priority** it lists **P0 today**, **P1 this week**, **P2 later** and **Known owned**, each with its open findings. **Audit settings** set a statement's priority and a cause's own, and a finding says where its priority came from. See [Read the audit page](/guides/audits#read-the-audit-page).
- **Audit settings** list under each statement only the causes its checks can reach (3.4.5). Statements whose checks share one run each show their own causes, so each cause's priority is set where it applies. See [Audit settings](/guides/audits#audit-settings).
- An audit's morning re-check can read HotWax returns by the return's Shopify order id (3.4.5), so older store-return findings matched that way are re-checked each morning.
- Each morning's re-check also reads the HotWax orders whose items were approved, completed or cancelled since the check's last read, when they were placed in the period (3.4.6). An order completed days after it was placed is now seen completed. See [How findings close](/guides/audits#how-findings-close).
- A check whose run read no records on one side, or kept none, while the other side read some, is **Not run** and closes nothing (3.4.6). The update after the run names the checks that did not run or partly ran, and says Darpan has been alerted. See [A check did not run](/troubleshooting/audits#a-check-did-not-run).
- An order paid in part, with that payment given back, is named by its cause even when HotWax shows its total as zero (3.4.6). An order whose card authorization was voided counts as never paid.
- A finding opens on its basics: each compared system's status, amount and day, **None** where a system has no record of it (app `v4.4.4`).
- The basics give each system's payment status beside its status, such as Completed · Settled (3.4.6, app `v4.4.7`). A check of completed Shopify returns now fills the Shopify status, total and day.
- While a play runs, a finding's row and its open detail agree (app `v4.4.7`). When a check closes the finding you have open, both say **Fixed**.
- An order finding can list its lines under **Order** (3.4.7, app `v4.4.10`): each line's SKU, each system's word for it, such as Shopify Unfulfilled · HotWax Completed, and its quantity. A Shopify line and its HotWax item are one row, and the rows line up in columns. From 3.4.8 you turn them on yourself: tick **Order lines** on a Shopify **Orders** side or **Order items** on a HotWax orders side, then **Sync** the automation. Both are off by default. See [Read the audit page](/guides/audits#read-the-audit-page).
- When a check did not run, the digest names its statement and says Darpan has been alerted, as the update after each run does (3.4.7). It no longer gives the read's error. See [Digests](/guides/audits#digests).
- Acknowledge a finding (3.4.9, app `v4.4.11`): choose **Acknowledge** on an open finding, write why it is known, and it moves from **open** to its own **acknowledged** pill, with who, when and the note on a card. It is not closed. **Remind me in 5 days if still open**, on by default, brings it back to **open** if a check has not seen it fixed by then. The pencil changes the note or the reminder, and **Reopen** puts it back. One acknowledgement covers the order's whole row. The update after each run and the digest count acknowledged findings on their own line. See [Acknowledge a finding](/guides/audits#acknowledge-a-finding).
- Send Darpan feedback from a finding (3.4.9, app `v4.4.11`): the speech bubble in the finding's head lists the notes your team sent on the same statement and cause in the last 2 weeks, and sends yours to the Darpan team with the finding attached. You get an email saying it arrived, and Darpan replies by email, never in the app. See [Send Darpan feedback on a finding](/guides/audits#send-darpan-feedback-on-a-finding).
- **Re-check all findings** (3.4.9, app `v4.4.11`): the circular-arrow icon beside the audit's name re-checks every open finding of the period, and the one at the head of the **Findings** column the open statement's. Each check's open findings are read once, by key; what was fixed since the morning check closes, and the page says, for example, **Re-checked 26. 20 closed, 6 still open.** It needs the same role as **Resolve finding**, and, like Resolve, does not count as a check run. In the app only. See [Re-check all findings](/guides/audits#re-check-all-findings).
- **Running now** says, for each read, about how many records it read last time, when it last moved and its rate, and during a peak period how lightly each system is read (app `v4.4.4`).
- A finding speaks of the systems its check compares and no others (3.4.12, app `v4.4.14`): a HotWax-to-NetSuite finding shows HotWax and NetSuite, even on a morning the check did not run. A system with no record of it reads **Missing**. HotWax's status shows when another system's record carries it, the day reads from NetSuite's own date, and a line's amount stands in when there is no order total.
- Every finding of a kind lists the same rows (3.4.12, app `v4.4.14`): an order's customer, sales channel and ship method; a return's channel; an exchange's warranty id. The per-system cards under the fix are gone; the basics row already says each system's status. A line is named by its SKU or HotWax item, never by the finding's id.
- An order lookup lists every open finding of the order (3.4.14), including findings a check keyed by another system's ids, such as a HotWax line that is not billed in NetSuite, matched through the records they name.
- The check that every approved HotWax order reaches NetSuite also reports completed orders, with their causes, and can name a retired SKU or a product missing in NetSuite (3.4.15). For an order NetSuite does not have, Darpan asks HotWax for its items, and only when no stronger cause already holds.
- Audit change proposals are for editors and admins in the CLI too, as in the app (3.4.15).
- A finding keeps the record its check looked up in another system (3.4.13), such as the HotWax order behind a Shopify cancellation, so it shows that system's status. A NetSuite line's finding also shows its HotWax ship method.
- **Re-check all findings** reports how many it checked and closed again (3.4.13). Since 3.4.10 the re-check ran but the page showed an error instead of its progress.
- Each statement shows its count on a morning its check did not run (app `v4.4.14`); **not checked** still says which did not run.

It drops `darpan scripts`, `script` and `deploy`, which stopped working when queries replaced tenant scripts; `darpan call` reaches the query methods.

- **Shopify exchange checking moved to a presence rule.** Every exchange created in Shopify within the return window is expected in OMS, and confirmed absences are reported as differences — returns still in transit are no longer reported as missing.

**Operators**

- Production images pin `DARPAN_REF=v1.2.0` with `darpan-hotwax`/`shopify-darpan` at `v0.5.0` — these move together, since this release's connector registry references services introduced in the v0.5.0 components.
- Deploy the backend before the app.
- The MySQL driver moves to Connector/J 9.7.0, which is what supports a MySQL 8.4 server — do not upgrade the database server ahead of this release.
- Scheduled automations resolve their tenant reliably and surface failures instead of ending quietly, so schedules that had stopped producing runs will start again.

**API**

- This release removes the two tenant-wide notification-setting methods, replaced by the chat-space methods, and adds twenty-six methods. The published contract version moves from `1` to `2`.
- Integrations calling the removed methods must move to the chat-space methods; backend and app pins must move together.

**Upgrade**

- Existing environments load twelve seed records (platform-admin API security, chat-space and run-subscription entity security, a cancelled-run status, and two connector-registry rows) via `./gradlew loadDarpanUpgradeData`.
- After that load, run the one-time internal service `reconciliation.ReconciliationNotificationServices.migrate#TenantNotificationSettings` once server-side — it copies each tenant's existing webhook into a chat space named "Default space" and links that tenant's automations to it. It is safe to run more than once; tenants that already have a chat space are skipped.
- Until it runs, tenants keep their webhook but see an empty chat-space list.

**Rollback**

- Schema and seed additions are additive, and the notification migration copies rather than moves, so the earlier webhook rows survive and `v1.1.0` behavior still works if the backend is rolled back.
- Keep the app on `v2.2.0` if the backend goes back to `v1.1.0` — app `v2.3.0` depends on the chat-space methods, which do not exist there.
- Roll all component pins back together.

**Product**
